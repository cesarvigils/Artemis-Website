# Artemis data contract (website <-> Discord bot <-> iRacing sync)

Version 1.2, 14 Sep 2026. Changes since 1.0: `results.entries` (1.1); `drivers.iracingId`, `events.startTime`, and the generated file `stats.json` (1.2). All additive; old records stay valid. Both the website (`preview` branch, Astro) and the Discord bot (`bot` branch) implement exactly this. Any change to this file must be applied on both sides.

## Where the data lives

Three JSON files in the website repo `cesarvigils/Artemis-Website`, on the branch that Vercel deploys (configurable in the bot as `GITHUB_BRANCH`; production is `master`, previews use `preview`):

- `src/data/results.json`
- `src/data/drivers.json`
- `src/data/events.json`

The bot is the writer (GitHub Contents API, one commit per command). The website is the reader (imports the JSON at build time; Vercel rebuilds on every push). Humans may still edit the files by hand; the bot must tolerate hand edits (re-read before every write, never cache across commands).

Every file is a JSON array, UTF-8, 2-space indent, LF line endings, trailing newline, records sorted as stated below. The bot writes files in exactly this format so diffs stay minimal.

## Common rules

- `id`: lowercase slug `[a-z0-9-]{3,80}`, unique within its file. Generated by the bot when omitted (see each type), editable never (remove + add instead).
- Dates: ISO `YYYY-MM-DD` strings. No times.
- Strings are trimmed; empty strings are not allowed except where "may be empty" is stated.
- `_placeholder` (boolean, optional): `true` marks sample data shipped with the preview. The site renders placeholder records like any other; the bot shows `(placeholder)` in lists so operators can remove them. New records written by the bot never carry the field.
- Unknown fields are preserved by the bot on edit (read-modify-write of the whole record) and ignored by the site.

## results.json  (sorted by `date` descending, then `position` ascending)

```json
{
  "id": "2026-09-06-suzuka-1000-gt3",
  "date": "2026-09-06",
  "event": "Suzuka 1000",
  "track": "Suzuka International Racing Course",
  "series": "iRacing Special Event",
  "class": "GT3",
  "position": 4,
  "drivers": ["Matthew Blackley", "Nolan Walker"],
  "note": "Two stops on strategy, no contact all race."
}
```

| `date` | string | ISO date, not in the future by more than 1 day |
| `event` | string | 2â€“80 chars |
| `track` | string | 2â€“80 chars |

## events.json  (sorted by `start` ascending)

```json
{
  "id": "2026-09-25-petit-le-mans",
  "name": "Petit Le Mans",
  "track": "Michelin Raceway Road Atlanta",
  "start": "2026-09-25",
  "end": "2026-09-27",
  "classes": ["GTP", "LMP2", "GT3"],

  "note": "Roster locks 19 Sep."
}
```

| Field | Type | Rules |
|---|---|---|
| `id` | string | default `<start>-<slug(name)>` |
| `name` | string | 2â€“80 chars |
| `track` | string | 2â€“80 chars |
| `start` | string | ISO date |
| `end` | string | optional ISO date â‰¥ `start` |

## stats.json  (GENERATED by the nightly iRacing sync; never edited by the bot or by hand)

`src/data/stats.json`. Written by `scripts/fetch-iracing.mjs` from GitHub Actions (`.github/workflows/update-stats.yml`, cron nightly + manual). The site treats it as optional: if the file is missing, empty, or a driver has no entry, nothing is shown for that driver. The bot ignores it (`/data status` may report its `updated` value).

```json
{
  "updated": "2026-09-14T09:00:12Z",
  "source": "iracing-data-api",
  "drivers": {
    "matthew-blackley": {
      "iracingId": 123456,
      "irating": { "sports_car": 5012, "formula_car": 2100, "oval": 3400, "dirt_oval": 1350, "dirt_road": 1350 },
      "safety": { "sports_car": "A 4.20", "oval": "B 3.10" },
      "recent": [
        { "date": "2026-09-12", "series": "IMSA Endurance", "track": "Suzuka", "car": "BMW M4 GT3", "start": 9, "finish": 4, "sof": 3120, "incidents": 2 }
      ]
    }
  }
}
```

Rules: keys of `drivers` are `drivers.json` ids; only drivers with an `iracingId` appear; `irating` categories are iRacing's five (missing categories omitted); `safety` values use the licence pattern from `drivers.stats.licence`; `recent` holds at most 10 official races, newest first. The site shows the category that matches the driver's `group` (`road` â†’ `sports_car`, `oval` â†’ `oval`) and the three newest `recent` rows on the team page. `check:data` validates `stats.json` when it exists but never fails the build because of it (it logs and ignores a malformed file, so a broken sync cannot take the site down).

## Bot write protocol

1. GET the file (Contents API) with its `sha`; parse; validate the whole array (reject the command if the existing file is invalid, and say which record).
2. Apply the change; re-sort; serialise per the format rules.
3. PUT with the previous `sha`, branch `GITHUB_BRANCH`, committer/author `Artemis Data Bot <bot@artemisesports.com>`, message:
   `data(<file>): <add|edit|remove> <id> (by <discord username> <discord user id>)`
4. On a 409/422 sha conflict, re-read and retry once, then fail with a clear message.
5. Reply with an embed (no emojis): what changed, the record, the commit short SHA, and "Live in about a minute once Vercel finishes building."

## Website validation

`npm run check:data` (also run automatically as `prebuild`) validates all three files against these rules and fails the build with `file:index: message` lines so an invalid write can never deploy (Vercel keeps the previous deployment when a build fails).
