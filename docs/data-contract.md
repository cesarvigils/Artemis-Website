# Artemis data contract (website <-> Discord bot)

Version 1, 14 Sep 2026. Both the website (`redesign` branch, Astro) and the Discord bot (`bot` branch) implement exactly this. Any change to this file must be applied on both sides.

## Where the data lives

Three JSON files in the website repo `cesarvigils/Artemis-Website`, on the branch that Vercel deploys (configurable in the bot as `GITHUB_BRANCH`; production is `maintenance`, previews use `redesign`):

- `src/data/results.json`
- `src/data/drivers.json`
- `src/data/events.json`

The bot is the writer (GitHub Contents API, one commit per command). The website is the reader (imports the JSON at build time; Vercel rebuilds on every push). Humans may still edit the files by hand; the bot must tolerate hand edits (re-read before every write, never cache across commands).

Every file is a JSON array, UTF-8, 2-space indent, LF line endings, trailing newline, records sorted as stated below. The bot writes files in exactly this format so diffs stay minimal.

## Common rules

- `id`: lowercase slug `[a-z0-9-]{3,80}`, unique within its file. Generated by the bot when omitted (see each type), editable never (remove + add instead).
- Dates: ISO `YYYY-MM-DD` strings. No times.
- Strings are trimmed; empty strings are not allowed except where "may be empty" is stated.
- `_placeholder` (boolean, optional): `true` marks sample data shipped with the redesign. The site renders placeholder records like any other; the bot shows `(placeholder)` in lists so operators can remove them. New records written by the bot never carry the field.
- Unknown fields are preserved by the bot on edit (read-modify-write of the whole record) and ignored by the site.

## results.json  (sorted by `date` descending, then `position` ascending)

```json
{
  "id": "2026-09-06-suzuka-1000-gt3",
  "date": "2026-09-06",
  "event": "Suzuka 1000",
  "track": "Suzuka International Racing Course",
  "series": "iRacing Special Event",
  "class": "GT3",
  "position": 4,
  "drivers": ["Matthew Blackley", "Nolan Walker"],
  "note": "Two stops on strategy, no contact all race."
}
```

| Field | Type | Rules |
|---|---|---|
| `id` | string | default `<date>-<slug(event)>-<slug(class)>`; if taken, append `-2`, `-3`, ... |
| `date` | string | ISO date, not in the future by more than 1 day |
| `event` | string | 2–80 chars |
| `track` | string | 2–80 chars |
| `series` | string | 2–60 chars (league or "iRacing Special Event") |
| `class` | string | one of: `GTP`, `LMP2`, `GT3`, `GT4`, `TCR`, `NASCAR Cup`, `NASCAR Xfinity`, `NASCAR Trucks`, `ARCA`, `Formula`, `Other` |
| `position` | integer | 1–99 |
| `entries` | integer | optional, 2–999: number of cars in the class/split, so the site can show `P4 / 41` |
| `drivers` | string[] | 1–6 names, each 2–40 chars, displayed in order; the site matches these names against `drivers.json` `name` to show each driver's latest finish |
| `note` | string | optional, max 140 chars |

Site usage: home "Recent results" = first 6 records; hero proof row = record with the lowest `position` among the newest 3 by date (ties: newest); partners page snapshot = first 3.

## drivers.json  (sorted by `group` order road, oval, crew; then by `number` numeric ascending, crew by `name`)

```json
{
  "id": "matthew-blackley",
  "name": "Matthew Blackley",
  "role": "driver",
  "group": "road",
  "number": "14",
  "country": "USA",
  "focus": "GT3 / Endurance",
  "bio": "One line, plain, no exclamation marks.",
  "stats": { "irating": 5012, "licence": "A 4.20" },
  "socials": { "x": "https://x.com/example", "twitch": "", "youtube": "", "instagram": "" },
  "active": true
}
```

| Field | Type | Rules |
|---|---|---|
| `id` | string | default `slug(name)` |
| `name` | string | 2–40 chars (real name or handle, the operator's choice) |
| `role` | string | `driver`, `pitwall`, `staff` |
| `group` | string | `road`, `oval`, `crew` (`crew` for pitwall/staff) |
| `number` | string | digits, 1–3 chars, or empty for crew |
| `country` | string | ISO 3166-1 alpha-3, uppercase (`USA`, `GBR`, `NLD`, ...) |
| `focus` | string | 2–40 chars, e.g. `GT3 / Endurance`, `NASCAR Trucks`, `Strategy` |
| `bio` | string | max 140 chars, may be empty |
| `stats.irating` | integer | optional, 0–15000 |
| `stats.licence` | string | optional, pattern `^[A-DRP] \d\.\d{2}$` (e.g. `A 4.20`) |
| `socials.*` | string | optional https URLs, may be empty; keys `x`, `twitch`, `youtube`, `instagram` |
| `active` | boolean | default `true`; inactive drivers are hidden on the site but kept in the file |

Site usage: home "Who drives" = first 4 active with `role: driver`; team page = all active grouped by `group`; `stats` renders only when present.

## events.json  (sorted by `start` ascending)

```json
{
  "id": "2026-09-25-petit-le-mans",
  "name": "Petit Le Mans",
  "track": "Michelin Raceway Road Atlanta",
  "start": "2026-09-25",
  "end": "2026-09-27",
  "classes": ["GTP", "LMP2", "GT3"],
  "status": "confirmed",
  "note": "Roster locks 19 Sep."
}
```

| Field | Type | Rules |
|---|---|---|
| `id` | string | default `<start>-<slug(name)>` |
| `name` | string | 2–80 chars |
| `track` | string | 2–80 chars |
| `start` | string | ISO date |
| `end` | string | optional ISO date ≥ `start` |
| `classes` | string[] | 1–4 values from the results `class` list |
| `status` | string | `planned`, `confirmed`, `done`, `skipped` |
| `note` | string | optional, max 140 chars |

Site usage: "Next race" strip = the first event whose `end` (or `start`) is today or later and whose status is `planned` or `confirmed`; if none, the strip shows "No race scheduled" with the last `done` event as a subtitle. The countdown targets `start` at 00:00 in the site's timezone (America/Chicago).

## Bot write protocol

1. GET the file (Contents API) with its `sha`; parse; validate the whole array (reject the command if the existing file is invalid, and say which record).
2. Apply the change; re-sort; serialise per the format rules.
3. PUT with the previous `sha`, branch `GITHUB_BRANCH`, committer/author `Artemis Data Bot <bot@artemisesports.com>`, message:
   `data(<file>): <add|edit|remove> <id> (by <discord username> <discord user id>)`
4. On a 409/422 sha conflict, re-read and retry once, then fail with a clear message.
5. Reply with an embed (no emojis): what changed, the record, the commit short SHA, and "Live in about a minute once Vercel finishes building."

## Website validation

`npm run check:data` (also run automatically as `prebuild`) validates all three files against these rules and fails the build with `file:index: message` lines so an invalid write can never deploy (Vercel keeps the previous deployment when a build fails).
